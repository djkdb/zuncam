# Troubleshooting

개발 중 **실제로 발생한** 문제만 기록한다. 각 항목은 발견 경로(테스트/스크린샷/로그)를 남긴다.

양식: Problem → Cause → Attempt → Why it failed → Final solution → 검증

---

## TS-01. 행동 계획이 마감이 먼 과제로 밤 12시까지 채워짐

- **발견**: 2026-09-26, 데모 데이터로 16:10 계획을 출력해 확인하던 중
- **Problem**: 풋살(18~20시)이 끝난 뒤 계획이 `21:40–23:10 운영체제 과제`, `23:20–24:00 운영체제 과제`로 채워졌다. 이 과제는 **D-5**, 180분짜리였다. 풋살 후 자정까지 쉬지 않고 과제를 하는 계획은 현실적이지 않다.
- **Cause**: Planner가 우선순위 순으로 빈 시간을 채우면서, 각 과제의 **전체** 예상 소요시간을 오늘 배치하려 했다. 마감까지 며칠 남았는지는 우선순위 점수에만 반영되고, 오늘 배치할 양에는 반영되지 않았다.
- **Attempt 1 (최초 구현)**: "모든 미완료 과제를 전부 배치 + 하루 최대 6시간 상한" — 상한만으로는 부족했다. 6시간 안에서도 D-5 과제가 남은 저녁을 다 가져갔다.
- **Final solution**: `todayShare(estimatedMinutes, daysLeft)` — 마감이 오늘/내일/지남이면 전부, 그보다 멀면 `남은 일수로 나눈 하루 몫`(10분 단위 올림, 최소 30분)만 배치. UI 이유 문구도 `남은 3시간 중` 대신 `오늘 몫 40분 중`으로 구분.
- **검증**: `tests/engine.test.ts` — "마감이 먼 과제는 하루 몫만 배치한다 (D-5, 180분 → 40분)". 수정 후 계획은 `21:40–22:20 운영체제 과제 (오늘 몫 40분)`에서 끝난다.
- **코드**: `src/lib/engine/planner.ts` `todayShare`

## TS-02. 문장에 "이(가)", "을(를)"이 그대로 노출됨

- **발견**: 2026-09-26, "지금 뭐 하지?" 결과 출력에서 `'CLASS FC 풋살' 이동 출발이(가) 17:20이므로…`
- **Problem**: 규칙 기반 문장이 한국어 조사를 괄호 병기로 출력해 부자연스러웠다. AI가 없을 때 사용자가 보는 문장이 전부 이 형태였다.
- **Cause**: 템플릿 문자열에 조사를 고정으로 적었다 (`${title}이(가)`).
- **Final solution**: `src/lib/korean.ts` — 마지막 글자의 받침 유무로 이/가, 을/를, 은/는, 과/와, 으로/로(ㄹ받침 예외) 선택. 마지막 글자가 한글이 아니면(예: `CLASS FC`) 괄호 병기 유지.
- **검증**: `tests/korean.test.ts`

## TS-03. AI 지연 시 서버가 브라우저보다 늦게 포기함 (50초 vs 30초)

- **발견**: 2026-09-26, 목 서버 `MODE=slow`(40초 지연)로 `/api/ai/conflicts` 호출
- **Problem**: 서버 응답까지 **50초**. 브라우저는 30초에 요청을 중단하므로 사용자는 30초를 기다린 뒤 폴백을 보고, 서버는 그 뒤로도 20초 동안 API를 붙잡고 있었다.
- **Cause**: SDK 타임아웃 25초 + `maxRetries: 1`. SDK는 **타임아웃도 재시도 대상**이라 최악 시간이 25초 × 2 = 50초가 된다. 두 타임아웃을 따로 정하면서 재시도를 곱하지 않았다.
- **Final solution**: 서버 타임아웃 12초 × 2회 = 최대 24초 < 브라우저 30초. 오류 메시지에도 `12000ms × 2회 초과`로 재시도 포함 사실을 표시.
- **검증**: 같은 목 서버로 재호출 → 약 25초(`latencyMs: 24396`)에 `timeout` 사유로 규칙 기반 폴백.
- **코드**: `src/lib/ai/client.ts`
- **남은 과제**: 실제 모델의 p95 지연을 측정해 12초가 충분한지 확인 (prompt-history.md "다음에 측정할 것").

## TS-04. (오판) 충돌을 만들었는데 Today에 충돌 카드가 안 보임

- **발견**: 2026-09-26, Playwright로 데모 시나리오 자동 실행 중
- **Problem**: 데모 시간 16:10에서 자연어로 "오늘 3시에 친구 약속 있어"를 추가(14~16시 수업과 겹침)했는데 충돌 카드가 나타나지 않았다.
- **Cause**: 버그가 아니었다. `buildCampusContext`는 **이미 끝난 오늘의 충돌은 숨긴다**(15:00~16:00 약속은 16:10에 이미 지남). 테스트 시나리오가 잘못됐다.
- **Final solution**: 코드는 그대로 두고, 시나리오를 미래 충돌("오늘 저녁 7시에 친구 약속" ↔ 18~20시 풋살)로 변경 → 충돌 카드·계획 경고·일정 페이지 경고 모두 표시 확인. 데모 스크립트(`demo-script.md`)에 "충돌은 현재 시각 이후로 만들 것"을 명시.
- **배운 점**: 저장 전 미리보기(`previewEventConflicts`)는 시간과 무관하게 충돌을 보여주므로, 과거 시간 입력 시에는 모달에서만 경고가 뜨고 Today에는 뜨지 않는다. 의도된 동작이지만 발표 중 혼동하기 쉽다.

## TS-05. 조언을 따르면 오히려 마감을 놓침 (시뮬레이션)

- **발견**: 2026-09-26, `npm run sim` 첫 실행. 하루 재생에서 오늘 마감 준수율 campus-os **78.3%** < 단순 EDF **84.0%**. 앱의 핵심 약속("따르면 된다")이 깨진 상태였다.
- **Problem** (random#23 재현): 09:00 마감·60분 과제를 08:00부터 하다가, 08:40에 다른 과제(내일 18:00 마감)로 전환 → 09:00 마감 놓침 → 마감이 지나자 다시 1위로 복귀 (A→B→A 번복, 전체 34건).
- **Cause**: Planner가 **우선순위 점수 순**으로 빈 시간을 채웠다. 점수의 '예상 소요' 요인이 *남은* 시간 기준이라, 20분 남은 순간 6점→1점으로 떨어져 추월당했다. 점수는 "무엇이 중요한가"이지 "언제 해야 마감을 지키는가"가 아니었다.
- **Final solution**: 우선순위(표시)와 배치 순서를 분리. 36시간 안에 마감되는 과제는 **마감 순(EDF)** 으로 배치, 그다음 마감 지난 과제, 나머지는 점수 순 (`planner.ts` `scheduleOrder`).
- **결과**: 준수율 78.3% → **85.8%**, 번복 34 → 18. 남은 번복은 TS-06에서 해결.

## TS-06. '오늘 몫'이 끝나지 않고, 앱이 진행 상황을 모름 (시뮬레이션)

- **발견**: TS-05 이후 남은 번복을 추적하다가.
- **Problem**:
  1. 마감이 먼 과제는 하루 몫(예: 180분/6일=30분)만 배치하는데, 30분 한 뒤 다시 계산하면 150분/6일 → 또 30분. 공강 날 페르소나가 하루 330분을 일했다.
  2. `campus-os-blind`(진행 기록 없음) 정책: 하루 평균 **186분** 동안 틀린 남은 시간으로 조언, 준수율 71.7%.
- **Cause**: 앱이 "오늘 얼마나 했는지"를 알 방법이 없었다. 예상 소요시간 하나로 총량과 남은 양을 동시에 표현하려 했다.
- **Final solution**:
  - 데이터 모델: `Assignment.progress[{date, minutes}]` 추가. `estimatedMinutes`는 총 예상, 남은 시간은 계산값.
  - 오늘 몫 = `(남은 + 오늘 한 것) / 남은 일수 − 오늘 한 것`.
  - '예상 소요' 점수는 **총 예상** 기준 → 진행해도 순위가 흔들리지 않음.
  - UI: "지금 시작" 집중 세션 → "기록하고 멈추기 / 완료", 과제 목록의 "+ 기록". 세션 진행 중에는 경과 시간을 미저장 진행으로 계산에 반영.
- **결과**: 번복 18 → **0**, 과제 시간 209 → 130분/일(마감이 먼 과제를 몰아서 하지 않음). 페이싱이 며칠 뒤 마감에 해가 없는지는 1주일 재생으로 검증 (`simulation.md`).
- **기존 데이터 호환**: 저장된 과제에 `progress`가 없으면 `[]`로 로드된다 (zod default).

## TS-07. 하루 작업 상한(6시간)이 지켜지지 않음 (1주일 시뮬레이션)

- **발견**: 1주일 재생 추가 후, heavy 부하에서 하루 최대 **538분**.
- **Cause**: 계획은 매 시점 다시 세워지는데, 상한은 "지금부터 계획할 양"에만 적용됐다. 이미 한 작업이 빠져 있었다.
- **Attempt 1**: 미완료 과제(`openAssignments`)의 오늘 기록 합계를 상한에서 뺌 → **528분**, 거의 그대로.
- **Why it failed**: (a) 과제를 **완료하는 순간** 그 과제가 미완료 목록에서 빠지면서 오늘 한 시간도 같이 사라졌다. (b) 초과분 상당수가 **내일 오전 9시 마감** 과제였는데, 이건 사실상 오늘 끝내야 하는 일이라 상한으로 막는 게 맞지 않았다.
- **Final solution**: 완료 과제 포함 전체 오늘 기록(`loggedTodayTotal`)으로 상한 계산. 오늘 마감·내일 아침(계획 시작+2시간 이전) 마감은 상한 예외로 두고 "권장 상한 초과" 경고.
- **결과**: heavy 하루 최대 538 → **362분**, 23시 이후 34 → 2분/주 (이후 TS-09 식사 수정으로 361분 · 7분/주). 마감 준수 93.4% → 93.2% (512건 중 1건 감소, D-18).

## TS-08. 규칙 기반 문장이 AI 검증기를 통과하지 못함 (시뮬레이션)

- **발견**: 불변식 `RULE_TEXT_UNVERIFIABLE` 34건. 예: "다음 일정: 2026-09-27 19:00 '스터디'" → 19:00이 허용 목록에 없음.
- **Cause**: 하루 종료(`day_over`) 문장이 내일 일정 시각을 언급하는데, 허용 시각 목록은 오늘 기준으로만 만들어졌다. 이 상태면 AI가 코드와 똑같은 말을 해도 "환각"으로 거부된다.
- **Final solution**: 해당 시각을 허용 목록에 추가. 이 불변식을 시뮬레이션에 상시 포함 (코드 문장 = AI가 따라 해도 되는 문장).
- **결과**: 34 → 0.

## TS-09. 점심시간이 지나면 다음 과제 블록이 밀림 (시뮬레이션)

- **발견**: '오늘 마감이 남았는데 쉼' 지표를 추적하던 중. 09:30에는 13:00 과제로 계획됐는데 12:10에는 16:00으로 밀림.
- **Cause**: 식사는 '지금 이후'에만 배치됐다. 12:00이 지나면 점심 12:00 후보가 탈락 → 12:30으로 밀림 → 13:30~13:45 틈이 25분 미만이 되어 과제가 16:00으로 밀림.
- **Final solution**: 이미 시작된 식사도 후보로 인정해 제자리에 둔다.
- **결과**: 계획 흔들림 1.0 → **0.7회/일**, 오늘 마감이 남았는데 쉼 5.6 → 4.9분/일 (수정 전 값은 해당 조건만 되돌려 같은 시나리오에서 측정).
- ⚠ **이 수정은 회귀를 만들었다** — '이미 시작된 식사'를 인정하자 10분마다 새 후보가 '진행 중'이 되어 점심이 2시간 넘게 늘어났다. TS-15에서 다시 고쳤다.

## TS-10. 자연어 규칙 파서 정확도 (코퍼스)

- **발견**: 코퍼스 36문장 중 28개 통과 (77.8%).
- **실패 유형**: "두시"(한글 숫자), "정오", "한 시간 반", "12일"(월 없음), "문제 5개 풀기"(과제 명사 없음), "조깅"/"과외" 분류, "오늘 뭐하지"를 일정으로 오인.
- **Final solution**: 각 유형 규칙 추가. 분류는 활동 > 장소 순으로 우선순위를 둠("카페에서 과외" → 개인). 날짜만 있고 활동이 없으면 해석하지 않음. AI 프롬프트(parse-v2)에도 같은 표현 규칙을 명시.
- **과적합 확인**: 틀린 문장만 고쳤으니 36/36은 당연하다. 수정 **이후** 새로 쓴 홀드아웃 20문장 → **18/20**. 실패 2건(단독 "90분")은 홀드아웃 보존을 위해 고치지 않았다.

## TS-11. 오늘 마감이 남았는데 "급하게 배치된 작업이 없어요"

- **발견**: TS-09 추적 로그. 12:10 "지금은 급하게 배치된 작업이 없어요" — 실제로는 오늘 마감 과제가 16:00에 계획돼 있었다.
- **Final solution**: 빈 시간/짧은 틈 문구가 다음 과제 블록과 시작 시각을 알려준다 ("식사 후 16:00부터 '선형대수 과제 4'를 할 차례예요"). 짧은 틈에는 "25분보다 짧은 틈에는 배치하지 않는다"는 이유를 함께 표시.
- 같은 로그에서 숫자로 끝나는 제목의 조사 오류('과제 4'을(를))도 발견 → 숫자 읽는 소리 기준으로 받침 판단.

## TS-12. 예상이 틀리는 학생 — 첫 가설(평균 보정)은 효과가 없었다

- **발견**: 행동 모델(아래 simulation.md) 도입 후, "예상이 틀리는 학생"(실제 = 예상 × 0.8~2.0, 평균 1.33)에서 EDF와의 격차가 커짐.
- **가설**: 계획이 예상 소요시간을 그대로 믿기 때문.
- **Attempt 1**: 완료 과제의 "기록 시간 / 예상"을 학습해 남은 과제에 곱하는 **예상 보정** (`computeCalibration`). 보정 자체는 정확했다(학습 1.35 vs 실제 1.32).
- **Why it failed**: 마감 준수율 변화 없음(91.6% → 91.6%). 평균 과소평가는 이미 "진행 기록 → 재계획"이 흡수하고 있었다. 격차의 원인은 다른 데 있었다 (TS-13·15·17).
- **이후**: 시뮬레이터를 공정하게 고친 뒤(TS-17) 다시 A/B 하니 보정 on이 off보다 +0.9~1.2%p (biased), 남은 시간 오차는 비슷 또는 소폭 감소. 효과는 작지만 일관돼서 유지하고, 설정에서 끌 수 있게 했다. 학습 결과는 설정·과제 화면에 그대로 보여준다.

## TS-13. 당일 마감을 식사·휴식 때문에 놓침 / 내일 마감 판단이 어림값이었음

- **발견**: EDF는 지키고 Campus OS는 놓친 과제를 분류 — 둘 다 같은 양(예: 360분)을 일했는데 Campus OS만 마감 후에 끝남.
- **Cause**:
  1. 계획이 마감이 걸린 날에도 식사 1시간·세션 사이 휴식 10분을 지켰다. EDF 기준선은 쉬지 않는다.
  2. "내일 아침(시작+2시간 이전) 마감이면 오늘 끝낸다"는 어림값이 내일 실제 시간표를 보지 않았다. 내일 12시 마감이어도 오전 수업이면 시간이 없다.
- **Final solution**:
  1. **크런치**: 오늘 마감 과제가 다 안 들어가면, 그 마감 전까지 식사·휴식을 빼고 다시 계획해 보고, 더 많이 들어가면 그 계획을 쓰며 경고한다.
  2. 내일 마감은 `freeMinutesOn(내일, 시작~마감)` × 0.6 을 넘는 만큼만 오늘 하루 상한에서 예외.
- **결과**: 이상적 학생 하루 재생 85.8 → 86.8%, heavy 1주일 91.5 → 92.6%.

## TS-14. 예상을 넘긴 과제를 "10분 남음"으로 봄

- **발견**: 실패 사례 추적. 실제 2배 걸리는 과제가 예상을 넘기면 앱은 10분 남았다고 보고, 하루 상한에 막혀 작업을 멈춤.
- **Final solution**: 예상을 넘기면 보정 예상의 30%(최소 30분)가 더 남았다고 본다.
- **결과 (A/B, 공정한 시뮬레이터)**: 10분 가정 대비 +0.3~0.6%p. 작지만 일관되고 논리적으로도 맞아 유지. 처음 측정(불공정한 시뮬레이터)에서는 오히려 −0.9%p로 보였다 — TS-17 참고.

## TS-15. 점심이 2시간 넘게 늘어남 (TS-09 수정의 회귀)

- **발견**: TS-14 추적 로그에서 `11:50 점심 13:00까지 → 13:00 점심 13:30까지 → 13:30 점심 14:00까지`.
- **Cause**: TS-09에서 "이미 시작된 식사는 유지"하도록 바꿨는데, 앱은 실제로 밥을 먹었는지 모른다. 12:30~13:30, 13:00~14:00 후보도 매 시점 "이미 시작된 식사"가 되어 식사가 계속 이어졌다. 식사 시간은 '쉼' 지표에서 제외돼 있어서 어떤 지표도 이를 잡지 못했다.
- **Final solution**: 식사 시각을 **현재 시각과 무관하게 그날의 고정 일정만으로** 정한다. 고정 일정은 하루 동안 바뀌지 않으므로 매 시점 같은 결과. 이미 끝난 식사는 생략. 회귀 방지 테스트("10분마다 다시 계획해도 식사는 하루 120분 이하, 점심 종료 시각은 하나") 추가 — 이전 로직에서 실패하는 것을 확인.
- **결과**: 식사 조언 132.7 → **77.7분/일**, 계획 흔들림 0.7 → 0.4회/일, heavy·늦게 따름 85.8 → 88.0%.
- **교훈**: 버그를 고칠 때 "그 버그를 측정하는 지표"가 없으면 수정의 부작용도 보이지 않는다. 식사 시간 지표를 시뮬레이션에 추가했다.

## TS-16. (기각) 마감이 걸린 과제에 여유분 확보

- **시도**: 과거 기록의 80% 분위 배율로 오늘·내일 마감 과제에 여유 시간을 더 배치 (크런치 판단에는 미사용).
- **결과**: 1주일 지표 +0.2~0.6%p(잡음 수준), **하루 재생 86.8% → 83.0%로 하락**. 예상이 정확한 학생에게는 여유분이 같은 날 마감인 다른 과제의 시간을 빼앗았다.
- **결정**: 되돌림. "현실적인 학생에게 도움"이 "정확한 학생에게 해"를 정당화하지 못했다.

## TS-17. 시뮬레이터 자체의 결함 3가지 — 비교가 불공정했다

제품이 아니라 **측정 도구**의 버그. 이 때문에 TS-12~16 도중의 일부 수치는 잘못 해석될 뻔했다.

1. **정책마다 다른 난수** — "딴짓하는 시각"을 정책별 난수로 뽑아, Campus OS와 EDF의 학생이 서로 다른 시각에 딴짓했다. → 공통 난수(날짜·시각·행동으로 결정)로 변경. "늦게 따름" 격차 4.1%p → 0.6%p: **대부분 잡음이었다.**
2. **전역 id 카운터** — 과제 id가 "앞에서 몇 개를 생성했는지"에 따라 달라졌고, 실제 소요 배율을 id로 정하므로 **같은 시드인데 정책마다 실제 작업량이 달랐다.** → 시나리오마다 id를 0부터. 결정성 테스트 추가.
3. **EDF가 이동 시간을 침범** — 10분 단위 재생에서 EDF 학생은 08:40에 10분을 통째로 일해 08:45 출발을 5분 침범했다. Campus OS 계획은 08:45를 지킨다. → "다음 10분 안에 일정·이동이 시작되면 못 한다"로 통일.

- **검증**: 수정된 시뮬레이터로 **이전 커밋의 엔진**과 현재 엔진을 각각 측정(git worktree). EDF 수치가 전후 완전히 같다 → 비교가 공정하다는 근거. 전/후 표는 `simulation.md`.
